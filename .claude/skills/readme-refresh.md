# README Refresh

Keeps a human-readable "what's new" section in the top-level `README.md`
current, using **git history as the source of truth**. This skill is
**docs-only**: it edits `README.md`, shows the diff, and stops. It never
bumps versions, creates git tags, builds artifacts, commits, or publishes
releases.

## When to Use

- "Update the README"
- "Refresh the changelog"
- "What shipped since the last entry?"
- "Summarize what's changed since v1.27.0"
- Slash-command trigger: `/readme-refresh` (also responds to
  `/changelog-refresh` if invoked that way)

## When NOT to Use

- **Cutting a versioned release** (bumping `package.json`, creating a git
  tag, updating `CHANGELOG.md`, publishing a GitHub Release). This repo
  already automates that end-to-end via **release-please**
  ([release-please-config.json](../../release-please-config.json),
  [.github/workflows/release-please.yml](../../.github/workflows/release-please.yml)) —
  do not duplicate or interfere with it. If the user wants a release cut,
  point them to that workflow (merge the standing release-please PR, or
  land Conventional Commits to `main` and let it open one), not this skill.
- Editing any doc other than the top-level `README.md` (not `CHANGELOG.md`,
  not `wiki/*`, not `CLAUDE.md`/`AGENTS.md`).
- Making code changes, running builds, or running tests. This skill reads
  `git log` and writes prose — nothing else.

## Repository Facts

**Re-verify these before relying on them — they can drift.**

- **Repo slug:** `xozai/CivicSecondBrain` (`git remote -v`). The `gh` CLI is
  installed and authenticated in this environment — use it to resolve PR/issue
  titles when a commit subject alone isn't descriptive enough.
- **README changelog location:** `README.md` currently has **no changelog
  section**. This skill's job is a **"## Recent Updates"** section — a
  lighter-weight, more-frequently-updated companion to the project's real,
  fully-automated `CHANGELOG.md` (see below). On first run (section doesn't
  exist yet), create it by inserting a new `## Recent Updates` heading
  immediately after the intro tagline/callout block and its horizontal rule,
  right before the existing `## What It Does` heading. On every later run,
  find and edit that existing section wherever it lives — don't re-derive
  its position.
- **How releases are actually tracked (do not touch this):** git tags
  (`vX.Y.Z`, e.g. `v1.27.2`), a `package.json` `"version"` field, and a
  fully automated `CHANGELOG.md` generated by **release-please** from
  Conventional Commit messages on every merge to `main`
  ([release-please-config.json](../../release-please-config.json)). Commits
  like `chore(main): release 1.27.2 (#190)` are release-please's own PRs —
  never hand-edit `CHANGELOG.md` or tags from this skill.
- **No "latest release" pointer line exists in README.md today.** Don't
  invent one. If a future run is explicitly asked for a dated/versioned
  entry (see Workflow step 3), only then add a one-line pointer under the
  new section's heading — and even then, treat the version number as
  informational text, not a real release action.
- **Directory themes to group commits by** (for readable, area-based
  bullets instead of a raw commit dump):
  - `app/` — Next.js frontend, API routes, and `app/lib/{ai,claude,wiki,
    scraper,parser,manifest}` core logic (chat, ingest, lint, briefing)
  - `scripts/` — CLI entry points (`ingest-seed.ts`, `lint-wiki.ts`,
    `scrape-check.ts`, etc.)
  - `wiki/` — only `SCHEMA.md`/`index.md` are committed; generated content
    (`topics/`, `decisions/`, `recommendations/`, `log.md`) is gitignored —
    see below
  - `e2e/` — Playwright smoke tests
  - `.github/workflows/` — CI, release-please, scheduled ingest/lint
  - `infrastructure/`, `Dockerfile`, `railway.toml` — deployment
  - `public/` — static assets/screenshots
- **Gitignored paths — never cite content from these, only that an area
  changed if a commit touches them:** `raw-sources/`, `chat-log/`,
  `wiki/decisions/`, `wiki/log.md`, `wiki/people/`, `wiki/queries/`,
  `wiki/recommendations/`, `wiki/topics/`, `node_modules/`, `.next/`,
  `dist/`, `build/`, `.env*`, `tsconfig.tsbuildinfo`, `playwright-report/`,
  `test-results/`, `.playwright-mcp/`, `.codegraph/`. (Full list in
  [.gitignore](../../.gitignore).)
- **Issue/PR reference convention:** commits follow Conventional Commits
  (`feat:`, `fix:`, `chore(scope):`, `refactor:`, `test:`, `docs:`) and
  GitHub auto-appends the merged PR number as `(#NNN)` to the squash-commit
  subject. Some commits also carry a `closes #NNN` footer linking a
  separate tracking issue (e.g. commit `3b1397b` — "closes #147"). When
  summarizing, link the PR number the same way existing README prose does
  (plain `#NNN`, or a markdown link to
  `https://github.com/xozai/CivicSecondBrain/pull/NNN` if the surrounding
  text already uses linked references).

## Commands

| Purpose | Command |
|---|---|
| Latest tag (may be none) | `git describe --tags --abbrev=0` |
| List all tags | `git tag -l --sort=-creatordate` |
| Commits since baseline | `git --no-pager log <baseline>..HEAD --oneline` |
| Touched files since baseline | `git --no-pager log <baseline>..HEAD --name-only` |
| Full commit body (for a subject that needs more context) | `git --no-pager log <baseline>..HEAD --format='%H %s%n%b'` |
| Today's date | `date +%Y-%m-%d` |
| Resolve a PR/issue title (optional, if `gh` available) | `gh pr view <n> --json title,body` / `gh issue view <n> --json title` |

## Workflow

1. **Determine the baseline.**
   Compare (a) the newest dated entry already present in README's
   `## Recent Updates` section (if the section exists) and (b) the latest
   git tag from `git describe --tags --abbrev=0`. Use whichever is more
   recent as the baseline commit/tag. Honor an explicit `--since <ref>`
   override from the user (a tag, SHA, or date). If there is no existing
   section and no tags at all, summarize full history from the first
   commit.

2. **Collect changes since the baseline.**
   Run the commits-since-baseline and touched-files commands above. Group
   commits into themes using the directory map in Repository Facts.
   Reference closed issues/PRs using the convention above when a commit
   subject or body mentions one. Skip any diff content confined to
   gitignored paths — note only that the area changed (e.g. "wiki content
   regenerated") without quoting specifics, since that content isn't in
   the repo to verify.

3. **Decide entry type.**
   - **Default:** add or update an **`### Unreleased`** subsection at the
     top of `## Recent Updates`. Do not invent a version number, tag, or
     date for it.
   - **Only if the user explicitly supplies an `x.y.z` version:** write a
     dated **`### vX.Y.Z — <today's date>`** entry instead (today's date
     from `date +%Y-%m-%d`), and update the section's "latest release"
     pointer line if one exists. This is still docs-only — it does not
     bump `package.json`, create a tag, or touch `CHANGELOG.md`/
     release-please's own state. Prefer the default path for this repo:
     release-please already owns real versioned releases, so an explicit
     version here is just a label on the README summary, not a release.

4. **Write the update.**
   Turn raw commit subjects into concise, capability-focused bullets in
   the same voice as the rest of the README (direct, user-facing, no
   commit-message jargon like "chore" or "refactor:" verbatim). Fold
   multiple small commits touching the same feature into one bullet.
   Preserve every other README section and every existing entry in
   `## Recent Updates` verbatim — only add/update the current baseline's
   content.

5. **Show the diff and stop.**
   Display the change (e.g. `git diff README.md`). Make no commits, tags,
   or pushes. If the user wants to publish this as part of an actual
   version release, point them at the release-please workflow — merging
   its standing release PR (or landing more Conventional Commits to
   trigger one) — not this skill.

## Output

- An edited `README.md` with an updated `## Recent Updates` section.
- A short report: the baseline used (tag/SHA/date), the number of commits
  summarized, and an explicit reminder that nothing was committed, tagged,
  or published — this repo's actual release process is release-please, run
  separately.
